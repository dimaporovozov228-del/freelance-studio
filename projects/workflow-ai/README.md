# Проект 3: Inbox Triage — спецификация, реализация впереди

Сценарий: локальный импорт обращений из разрешённого JSON/CSV, классификация, приоритет, черновик ответа, очередь проверки человеком. Исходящие сообщения автоматически не отправляются.

Минимальный стек: Python + SQLite + простой локальный интерфейс. Сначала детерминированные правила и шаблоны без расходов на ИИ. Необязательный адаптер модели добавляется отдельно, после выбора провайдера, согласия на передачу данных и лимита стоимости.

Данные: messages(source, external_id unique per source, body, received_at); decisions(message_id, category, confidence, rationale, model_version); drafts(message_id, text, state, reviewer); events(entity_id, action, timestamp). Состояния imported → classified → draft → approved/rejected. Отправка находится за границей демо.

Поток: импорт → проверка схемы → дедупликация → маскирование персональных данных → категория billing/support/sales/unknown → шаблон → ручная редактура и подтверждение → экспорт. Для low-confidence или unknown обязательна ручная классификация. Содержимое обращений трактуется как данные, никогда как команды агенту.

Адаптер модели: classify(redacted_text) → строгий JSON по схеме; таймаут, максимум одна повторная попытка, лимит символов/токенов, журнал версии, возврат к правилам при ошибке. Нет инструментов доступа к почте, оплатам или секретам. Модель не меняет состояние approved.

Приёмка: 30 синтетических обращений, отдельная размеченная выборка; отчёт accuracy/confusion matrix только по реально полученным результатам; тесты дублей, неизвестной категории, сбоя провайдера, некорректного JSON, prompt injection, запрета автоодобрения. Любое изменение решения отражается в аудите. Демонстрация полностью работает без API-ключа.

Этапы: импорт+SQLite → правила+шаблоны → очередь проверки → тестовая выборка+отчёт → необязательный модельный адаптер с измерением стоимости и качества. Оплачиваемая инфраструктура до отдельного решения не требуется.
